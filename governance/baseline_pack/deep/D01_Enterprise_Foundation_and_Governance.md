# D01 — Enterprise Foundation & Governance (الأساس المؤسسي والحوكمة)
**Template:** MISHEL_MODULE_DEEP_DIVE_TEMPLATE v1.0 | **Version:** v1.0.0 | **Depth:** D5 (هدف) | **الحالة:** `SPEC DRAFT — لم يُقارَن بالكود بعد` (كل حالة COVERED/GAP أدناه `UNKNOWN` حتى فحص R0/Forensic)
**ملاحظة:** كل ما يخص قانون/ضرائب/تأمينات/معايير = `PENDING EVIDENCE`. الأرقام العتبية (DOA، SLA) أمثلة قابلة للتغيير بقرار Owner العميل، وليست قيمًا ثابتة.

## 1) الهوية
- **الاسم:** Enterprise Foundation & Governance · **العائلة:** Platform Core (Tenant/Org/Identity/Approval/Master Data/Config/Audit)
- **Tier:** T0 (لا يعمل شيء آخر بدونه) · **المالك:** Platform Architect + Owner
- **يعتمد عليه:** كل الموديولات D02–D20. **يعتمد على:** لا شيء.
- **IDs:** تُملأ من STEP17 عند الربط (`REQ-FND-*`, `WP-FND-*`).

## 2) الغرض والمستخدمون
**المشكلة:** شركة مقاولات كبيرة مجموعة كيانات قانونية، فروع، مشاريع، مشاريع مشتركة (JV)، أقسام، وعملات، وكلٌّ بصلاحيات واعتمادات مختلفة. بدون أساس صحيح كل موديول لاحق يعيد اختراع الهيكل ويتناقض.
**Personas وأهم مهامها:**
| Persona | أهم المهام |
|---|---|
| مالك النظام (Platform/Tenant Admin) | إنشاء الشركة، تفعيل الموديولات، إعدادات الدولة، المستخدمون |
| CEO / CFO / المدير العام | هيكل الشركة، مصفوفة الصلاحيات المالية (DOA)، التقارير الموحدة |
| مدير المشروع | مشروعه وفريقه وصلاحياته |
| مدير مالي/محاسب | الكيانات القانونية، العملات، الفترات |
| مدير الموارد البشرية | الهيكل الوظيفي والأدوار |
| مسؤول بيانات رئيسية (Master Data Steward) | الموردون، العملاء، المقاولون، الأصناف، الوحدات |
| مدقق داخلي/خارجي | سجل التدقيق، الصلاحيات، SoD |
| مسؤول تقنية (IT) | SSO، الأجهزة، التكاملات، الأسرار |
**مقياس النجاح (يحدده Owner):** زمن إعداد شركة جديدة جاهزة (Setup Wizard) · عدد الخطوات لإنشاء مشروع · صفر ثغرات في اختبارات العزل والصلاحيات · نسبة تغييرات الإعداد دون كود (هدف 100% لما يخص الشركات).

## 3) السيناريوهات (Given/When/Then)
**S1 — إعداد شركة جديدة:** Given عميل جديد · When يشغّل Setup Wizard ويختار دولة ونوع نشاط (مباني/بنية تحتية/ميكانيكا/…) · Then يُنشأ مستأجر + كيان قانوني + شجرة مراكز تكلفة مبدئية + أدوار قياسية + قوالب الاعتماد + عملة أساس، وكلها قابلة للتعديل.
**S2 — كيان جديد داخل مجموعة:** إضافة شركة تابعة بعملتها وتقويمها المالي وحسابات مستقلة وتجميع (Consolidation) للأعلى.
**S3 — مشروع جديد:** ينشأ تحت كيان قانوني، بعميله، عقده، فريقه، ميزانيته، قالب اعتماداته، ومركز تكلفته. يرث إعدادات الشركة ويتجاوز ما يلزم.
**S4 — JV/ائتلاف:** مشروع بشريكين أو أكثر بنسب، يظهر لكل شريك حصته فقط، وللمدير المشترك كله.
**S5 — تفويض صلاحية (Delegation):** مدير مسافر يفوّض نائبه لفترة، يُسجل ويُنهى تلقائيًا ولا يتجاوز حدود الدور.
**S6 — اعتماد حسب DOA:** أمر شراء 480k يمر بمدير مشروع، و3M تضيف المدير المالي، و10M تضيف CEO (أمثلة). تغيير العتبة بإعداد لا كود.
**S7 — منع الاعتماد الذاتي (SoD):** منشئ الأمر لا يعتمده، ومعتمد الدفع لا ينشئ المورد.
**S8 — دخول مستخدم من مستأجر آخر:** رفض قاطع ومسجل.
**S9 — مغادرة موظف:** تعطيل الحساب، إعادة إسناد المهام المعلقة والاعتمادات، حفظ سجله.
**الحالات الحدية:** مستخدم في أكثر من كيان بأدوار مختلفة · مشروع ينتقل بين كيانين · تغيير DOA أثناء وجود مستندات معلقة (القاعدة: المستندات المعلقة تُقيَّم بالقاعدة الساريه وقت التقديم ما لم يقرر Owner غير ذلك، قابل للإعداد) · عملة كيان تتغير (ممنوع بعد وجود قيود إلا بإجراء خاص).

**هرم الهياكل:** `Tenant` ← `Group` ← `LegalEntity` ← `Branch/BusinessUnit` ← `Project` ← `WBS/CostCenter`. وهيكل آخر مستقل: `Department` و`Position` و`Team` (مصفوفي).

| Tenant | id, name, region/residency, plan, status, locale defaults, retention policy | Platform |
| LegalEntity | tenant_id, legal_name (ar/en), registration/tax IDs, country, base_currency, fiscal_calendar, timezone, parent_entity, consolidation_flag | D13 يستهلك |
| Branch/BusinessUnit | entity_id, type (HO/regional/site-office), address, manager | Foundation |
| Project | entity_id, code, name, client_party_id, contract_ref, type, status, dates, location (geo), currency, JV_flag, cost_center_root | Foundation (الهوية) + D04/D05 (التفاصيل) |
| ProjectParticipant (JV) | project_id, party_id, share%, role (lead/partner), valid_from/to | Foundation |
| User | tenant_id, identity (SSO/local), status, language, MFA, linked_employee_id | Identity |

**قواعد النموذج:** كل جدول يحمل `tenant_id` + (`entity_id`/`project_id` حسب الحاجة) وتُطبَّق عليه RLS · الإصدارات والزمن (Temporal) للمرجعيات والقواعد (valid_from/to) · لا حذف صلب للكيانات المالية/التعاقدية (Soft/Archive مع سبب) · الأطراف: كيان واحد لكل منشأة حقيقية بمنع التكرار (مطابقة بالرقم الضريبي/السجل التجاري + تشابه الاسم) ودمج موثق (Merge) · البيانات الشخصية مصنفة (PII) في حقول موسومة.

## 5) دورة الحياة والـ Workflow
**State Machines:**
- Project: `Draft → Active → OnHold ↔ Active → Completed → Closed → Archived` (Closed يمنع الحركات المالية الجديدة؛ إعادة الفتح بصلاحية وسبب).
- Party: `Draft → PendingApproval → Approved → Suspended/Blacklisted → Merged/Archived`.
- ApprovalInstance: `Pending → Approved/Rejected/Returned → (Escalated) → Completed/Cancelled`.
- ConfigItem: `Draft → Review → Approved → Effective → Superseded`.
- User: `Invited → Active → Suspended → Offboarded`.
**Maker-Checker:** كل تغيير في: DOA، الأدوار الحساسة، بيانات الأطراف المالية (حساب بنكي)، الفترات المقفولة. المعتمد غير المنشئ.
**SLA والتصعيد:** مهلة لكل خطوة؛ عند التجاوز تذكير ثم تصعيد للمستوى الأعلى أو النائب المفوَّض. كلها إعدادات.
**الرجوع:** الاعتماد يمكن Recall قبل الخطوة التالية؛ بعدها يُعكس بإجراء معاكس مسجل لا بتعديل.

## 6) الصلاحيات
- **RBAC** (أدوار قياسية: Owner, CFO, PM, QS, Planner, Procurement, Storekeeper, Site Eng, QA/QC, HSE, HR, Accountant, Auditor-ReadOnly, IT Admin) + **ABAC** (قيود: الكيان، المشروع، القسم، مبلغ، تصنيف السرية، الموقع الجغرافي).
- **صلاحيات على مستوى الحقل** للحقول الحساسة (رواتب، أسعار تفاوض، حسابات بنكية).
- **SoD Matrix مُهيأة:** أزواج ممنوعة (إنشاء/اعتماد، إنشاء مورد/دفع، استلام/فاتورة…) مع استثناءات موثقة بموافقة.
- **Break-glass:** وصول طارئ بزمن محدود، مبرر، ومراقب، يُرفع فورًا للمدقق.
- **التدقيق:** كل قراءة لبيانات تصنيفها عالٍ، وكل تغيير صلاحية، يُسجل.
- **اختبار إلزامي:** كل endpoint له اختبار «بدون صلاحية → 403» و«مستأجر آخر → لا يرى».

## 7) الأحداث والربط التلقائي
**منتج:** `tenant.created` · `entity.created/updated` · `project.created/status_changed/closed` · `party.approved/suspended/merged` · `user.activated/offboarded` · `role.assigned/revoked` · `delegation.started/ended` · `doa.rule_changed` · `config.effective`.
**مستهلكون:** D13 (إنشاء دفاتر/مراكز تكلفة للمشروع)، D05 (WBS مبدئي)، D12 (إسناد موظفين)، D06/D07 (إغلاق الشراء لطرف موقوف)، D15 (مجلدات المشروع)، D18 (أبعاد التقارير).
**قواعد:** كل حدث بـ Idempotency key وإصدار مخطط وترتيب لكل مجمّع (Aggregate)، Outbox pattern، Dead-letter. مثال أثر: `party.suspended` ← يمنع إنشاء PO جديد لهذا المورد فورًا ويحذر عند المستندات القائمة.

## 8) الواجهات البرمجية (مبادئ)
- REST/OpenAPI + نسخ (`/v1`)، أخطاء موحدة (Code, Message, TraceId)، تقسيم صفحات، فلترة، ETag/If-Match لمنع التضارب.
- SCIM/SSO (OIDC/SAML) لإدارة المستخدمين.
- Webhooks موقعة لأحداث §7. Rate limits لكل مستأجر.
- MCP/Tools للوكلاء: قراءة هيكل الشركة والمشاريع فقط بصلاحية المستدعي.
- كل عملية ذات أثر تقبل `Idempotency-Key`.

## 9) الواجهة (UX)
- **Setup Wizard** (≤ 10 خطوات، يعمل بقوالب لنوع الشركة، يحفظ ويستأنف).
- شاشة هيكل الشركة (شجرة تفاعلية) وإنشاء مشروع في خطوات قليلة بقالب.
- لوحة DOA بصرية (جدول مبالغ × مستندات × خطوات) مع محاكاة «ماذا لو أنشأت أمر بمبلغ X؟».
- مركز الاعتمادات: صندوق واحد لكل المستندات مع فلاتر وتفويض سريع وموبايل.
- RTL/LTR كامل، عربي/إنجليزي، تواريخ هجري/ميلادي حسب الإعداد، Offline للقراءة على الموبايل.
- حالات فارغة تقود لأول خطوة، ورسائل أخطاء بشرية.

## 10) القواعد والحسابات
- حل DOA: يُختار أخص قاعدة مطابقة (مشروع > كيان > عام) ثم أصغر نطاق مبلغ يحتويه المبلغ بعد التحويل لعملة القاعدة بسعر معتمد يوم التقديم.
- تراكم المبالغ (Split-order prevention): تجميع أوامر نفس المورد/البند في نافذة زمنية قابلة للإعداد لمنع تفتيت الأوامر لتجنب عتبة أعلى.
- تسلسل الترقيم: لا إعادة استخدام، فجوات مسجلة، بنمط مرن (`{ENT}-{PRJ}-{TYPE}-{YY}-{SEQ}`).
- مطابقة تكرار الأطراف: normalization للأسماء العربية (همزات، ياء/ألف مقصورة، حذف ألقاب) + الرقم الضريبي + الهاتف؛ حد اشتباه قابل للضبط وقرار بشري عند الاشتباه.
- كل قاعدة بمصدرها وإصدارها وتاريخ سريانها.

## 11) المخرجات والتقارير (Output Factory)
هيكل الشركة (PDF/Excel) · مصفوفة DOA الحالية والتاريخية · مصفوفة الصلاحيات/SoD لكل مستخدم (للمدققين) · سجل المستخدمين المنتهية · تقرير التفويضات النشطة · سجل تغييرات الإعدادات · تقرير الأطراف المكررة المشتبهة.
التعلم من مثال: قالب «Authority Matrix» الخاص بالعميل يُرفع كمثال فيُشتق منه مولد مخرجات بنفس تنسيقه، بعد مراجعة بشرية (Output Factory).

## 12) التكاملات
- **هوية:** Azure AD/Entra، Google Workspace، Okta (OIDC/SAML)، SCIM — اتجاه: هوية ← MISHEL.
- **SAP/Odoo/محاسبة قائمة:** استيراد الهيكل (Company Codes/Cost Centers/Vendors) مع Mapping وتقرير فروق.
- **HRIS:** مزامنة الموظفين والأقسام.
- **Excel:** استيراد أطراف وأصناف مع معاينة وتحقق قبل الاعتماد.
- **n8n/Webhooks:** إشعارات الأحداث (خارجية، ليست مصدر منطق).
- لكل تكامل: Mapping موثق، إعادة محاولة، Dead-letter، تسوية دورية.

## 13) الذكاء الاصطناعي
- **Setup Copilot:** يقترح هيكلًا وقوالب DOA من وصف الشركة (Shadow → Assist)، وكلها تحتاج اعتماد بشري.
- **Master Data Assistant:** يكتشف تكرار الأطراف ويقترح الدمج؛ لا دمج تلقائي (HITL).
- **Access Reviewer:** يقترح سحب صلاحيات غير مستخدمة ويكتشف مخالفات SoD؛ القرار بشري.
- **Config Explainer:** يشرح لمن أثر تغيير الإعداد.
- **حدود:** لا يغير صلاحيات أو DOA بنفسه، لا يرى ما لا يراه المستخدم، كل ما يخص مال يمر بمراجعة. Evals على عينة هياكل وأطراف مكررة فعلية (مجهّلة).

## 14) العالمية والامتثال (`PENDING EVIDENCE`)
- Country Packs: لغة، عملة، ضرائب، فترات مالية، تقويم عطلات، نماذج رسمية، صيغ هوية/سجل تجاري/رقم ضريبي.
- مصر وغيرها: متطلبات الفاتورة الإلكترونية والتأمينات والضرائب والعمل تُتحقق من مصادر رسمية بتاريخ قبل أي ادعاء (سياسة الحداثة).
- إقامة بيانات (Data Residency) حسب المنطقة والعميل.
- وثيقة اعتماد دولية للأمن (ISO 27001/SOC 2) كمسار لاحق، وليس ادعاءً حاليًا.

## 15) الأمان والخصوصية والتدقيق
- Threat model مختصر: تجاوز المستأجر، تصعيد صلاحيات، سرقة جلسة، استغلال Break-glass، حقن عبر الاستيراد، تسريب عبر AI.
- RLS على كل جدول + اختبارات تلقائية في CI. مفاتيح تشفير لكل مستأجر (هدف) · تشفير نقل وتخزين · أسرار في خزنة.
- MFA إلزامي للأدوار المالية والإدارية. سياسة كلمات سر/جلسات/أجهزة.
- Audit append-only مع تجزئة تسلسلية لاكتشاف العبث، احتفاظ حسب السياسة.
- تصدير/حذف بيانات المستأجر (Offboarding) بإجراء موثق.

## 16) الأداء والتوسع
- أحجام تصميمية (للتأكيد مع Owner): مستأجرون بالمئات، كيانات عشرات، مشاريع بالآلاف، مستخدمون بعشرات الآلاف، أطراف مئات الآلاف.
- قراءة الصلاحيات مخبأة (Cache) مع إبطال فوري عند التغيير.
- شجرة الهيكل بـ closure-table/materialized path لاستعلامات سريعة.
- أهداف p95 للاستعلامات الأساسية يحددها Owner قبل القياس. اختبار تحميل لتقييم الاعتمادات المتزامنة.

## 17) الترحيل والبدء
- استيراد: هيكل، مستخدمون، أطراف، أصناف، DOA من Excel أو ERP قائم، بمراحل: Dry-run ← تقرير أخطاء ← اعتماد ← تنفيذ ← تسوية.
- قوالب جاهزة حسب نوع الشركة (مباني/طرق/مياه/طاقة/صناعي) وحسب الدولة.
- تنظيف الأطراف قبل الاستيراد (اكتشاف التكرار).

## 19) معايير القبول وDoD
- **AC-FND-01:** Given شركة جديدة When تنتهي Setup Wizard Then تتاح كل الأدوار والقوالب والكيانات وتجتاز T-FND-001 دون تدخل مبرمج.
- **AC-FND-02:** Given مستند بمبلغ على عتبة DOA When يُقدَّم Then يمر بالخطوات الصحيحة بالضبط ويُسجل سبب اختيار القاعدة.
- **AC-FND-03:** Given أي مستخدم When يحاول عملية خارج صلاحيته أو مستأجره Then تُرفض ويُسجل ولا يتسرب وجود السجل.
- **AC-FND-04:** Given تغيير في DOA أو صلاحية حساسة When يُعتمد Then يحتاج معتمدًا ثانيًا ويظهر في سجل التدقيق مع قبل/بعد.
- **AC-FND-05:** Given طرف بنفس الرقم الضريبي When يُنشأ Then يُحذَّر ويُمنع التكرار إلا بقرار موثق.
